## 一、定位与目标

层 README 是该层**总览 + 导航**页——回答「这层有哪些子模块、各做什么、怎么串起来」。
读者是全局导航者（跨层浏览、新成员），追求**一次看完层全貌，逐项导航到模块 / 组件文档**。

**目标**：它是「地图」，不是「内容」。层 README 只给「组件表 + 设计要点」，不承载实现
细节——实现细节在模块对外接口文档与组件子文档。

## 二、与其他文档的分工

| 文档 | 层级 | 回答 | 读者 |
| --- | --- | --- | --- |
| **层级 README** | 层（`app/<layer>/`） | 这层有哪些子模块、怎么串 | 全局导航 |
| 模块对外接口文档 | 模块（`app/<layer>/<module>/`） | 模块对外提供什么接口、怎么调用 | 外部调用方 |
| 组件子文档 | 组件（模块内单个 `.py`） | 组件怎么设计、边界、决策 | 内部维护者 / 集成方 |

**边界**：层 README 只给「组件表 + 设计要点」，细节链接模块文档 / 组件子文档，不搬内容
——双处维护必然漂移（Rule 1「一个事实一个家」）。

## 三、编写原则

1. **总览 + 导航**：子系统只给「组件表 + 设计要点」，细节链接子文档，不把子文档内容搬进
   README（避免双处维护）。
2. **以实际代码为准**：子模块结构以 `app/` 实况为准；旧文档与代码不符时以代码为准并标注。
3. **状态徽标对齐架构文档**：✅ 已实现 ｜ 🔶 进行中 ｜ ⬜ 待规划。
4. **结构 / 依赖图代码块一律指定 `text` 语言标识**，禁止裸代码块。
5. **配置只做导航**：配置项完整表在配置文档 / 模块文档；层 README 给「配置 → 模块」指向，
   不复制全表。
6. **写当前状态，不写历史**：只描述当前层结构；演进叙事（日期、修复、重构）归
   git commit + issues + ADR。

## 四、标准结构

```text
# <层名>说明文档
> 元信息引用块：对应代码 / 更新日期 / 文档定位 / 实现状态

## 📋 目录

## 模块概述
  核心功能（一句话） + 模块结构树（text 代码块） + 设计原则 + 依赖关系

## 实现状态总览
  子模块 × 文件 × 状态 × 核心内容 表

## <各子系统>一节
  每个子模块一节：核心功能 + 组件表（细节链接模块文档）

## 典型调用链路
  一条主链路：外部调用方 → 各子模块

## 配置关联
  配置 → 模块导航（全表在配置文档）

## 相关文档
  架构 + 各模块文档 + 组件子文档
```

### 结构要点

1. **各子系统一节 = 组件表 + 一句话职责**：细节链接模块文档，不展开实现。
2. **实现状态总览用表**：`| 子模块 | 文件 | 状态 | 核心内容 |`，状态徽标对齐架构文档。
3. **典型调用链路**：一条主链路串联各子模块，标注每环节职责，不并列展开所有路径。
4. **配置关联只导航**：每模块一行「配置见 [xxx.md]」，完整表在配置文档。

## 五、创建 / 优化流程

1. **核对代码**：子模块结构以 `app/<layer>/` 实况为准（不凭记忆）。
2. **总览 + 导航**：子系统只给组件表，细节链接模块文档 / 组件子文档（Rule 1）。
3. **同步引用**：新增 / 重命名 / 删除子模块、改设计或状态时更新层 README（CLAUDE.md
   硬性约定），并同步各模块文档的链接。
4. **校验**：跑 `uv run python -m scripts.verify_alignment`，通过后提交。
5. **避免冗余**：与模块文档 / 组件子文档重复的内容只留一处。
