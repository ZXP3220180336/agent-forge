## 一、定位与目标

独立子文档是层级 README（总览 + 导航）之下的**单个模块/组件**说明文档，回答两类问题：

- 调用方：「这个组件怎么用？」——接口契约
- 维护者：「为什么这样设计？」——设计动机

**目标**：契约可查、动机可溯、与代码零漂移。子文档不替代代码（Docstring / 测试承载实现与行为），只做契约与决策的权威记录。

## 二、文档类型分类（Diátaxis）

工业界（Diátaxis 框架：Tutorial / How-to / Reference / Explanation）把组件文档拆成两类，**分节隔离，不混写**：

| 类型 | 回答 | 内容 | 面向 |
| --- | --- | --- | --- |
| Reference（使用参考） | 「怎么调用」 | 接口契约：方法签名、参数、返回、配置、异常、行为边界 | 调用方 |
| Explanation（设计解释） | 「为什么这样」 | 设计动机、备选方案、权衡、决策记录 | 维护者 |

同一份子文档可两者兼具，但结构上分离（如「接口契约」节 +「设计决策」节），禁止在叙述中混合。

## 三、工业级原则

1. **docs-as-code**：文档进仓库、随代码同一 review 流程提交；路径镜像源码结构（`app/x/y.py` ↔ `docs/x/y.md`）；用脚本校验对齐（本项目 `scripts/verify_alignment.py` + `docs/ALIGNMENT.md`）。
2. **契约优先**：方法签名、参数默认值、返回结构、配置项等硬契约排最前、最精确。文档中的代码分三类处理：
   - **禁止完整复制生产代码**：实现细节由 docstring 承载，避免双源维护（源码改动需同步文档）
   - **允许关键逻辑示意**：解释设计的核心片段（状态机转移、锁外 sleep、防竞态等）可保留，但须精简并标注「示意，完整实现见源码」
   - **允许参考实现代码**：源码已从生产移除、文档是唯一载体时（如 limiter.md 的 5 类限流算法），完整保留并声明
3. **状态标注**：状态徽标（✅ 已实现 / 🔶 进行中 / ⬜ 待规划 / ❌ 已废弃）+ 更新日期，与 ALIGNMENT 表联动；废弃组件标 ❌ 而非默默消失。
4. **轻量克制**：过度文档化是反模式（documentation rot）。组件越简单，文档越短；文档只做契约与决策的导航，行为的权威在测试。
5. **不描述非相关模块**：模块文档不描述【不被当前模块依赖】或【不依赖当前模块】的非相关模块信息（职责 / 位置 / 边界）。相关与否的判据 = 是否存在端口 / 调用依赖；并行层（如集成层与基础设施层）互不依赖即互非相关，各自职责只写在自己文档与 architecture.md，不互相描述。

## 四、粒度分级：简单组件 vs 复杂组件

不是每个组件都要长文档。按复杂度选粒度：

| 判定 | 简单 / 稳定组件 | 复杂 / 高风险组件 |
| --- | --- | --- |
| 特征 | 方法少（≤5）、行为稳定、契约清晰、无重大设计权衡 | 状态多（重试/熔断/限流/整流）、设计有备选方案与权衡 |
| 粒度 | 轻量 Reference（约 80 行） | 完整设计文档（含备选方案对比、决策记录、边界取舍） |
| 结构 | 模板 A（见下） | 模板 B（见下） |
| 本仓库案例 | `cost_tracker.md`（纯静态 4 方法，精简后 82 行） | `limiter.md`（限流，含 5 类算法对比、问题→修复→工业对照） |

**写之前先判定**：组件属于哪类，再选模板。简单组件写成重量文档 = 维护负担；复杂组件写成轻量文档 = 契约不完整。

## 五、标准模板

### 模板 A：简单组件（轻量 Reference，~80 行）

```text
# <组件名> <主题>说明文档
> 元信息引用块：模块 / 更新日期 / 职责 / 状态 / 配套
## 📋 目录
## 定位与职责        ← 2-3 句 + 要点；外部数据（定价表/常量）以源码为准，不整表复制
## 接口契约          ← 方法签名表（类型/默认值/返回结构）+ 公式/关键语义
## 行为边界          ← 容错场景表（None/缺失/非法/边界）
## 使用示例          ← 1-2 段最小示例
## 设计决策          ← 简短：仅关键权衡，如「为什么按长度降序」
## 测试              ← 引用测试文件（行为契约权威来源）
## 相关文档          ← 主文档 + 同级组件 + 配置
```

### 模板 B：复杂组件（完整设计文档）

模板 A 基础上扩展，**完整章节顺序与每节内容规范见
[六、标准结构](#六标准结构复杂组件完整章节顺序)**——从 `client.md` / `limiter.md` / `retry.md` /
`streaming.md` / `streaming_rectifier.md` 五份复杂组件文档总结。

> 组件详解中的代码只允许「关键逻辑示意」（标注出处）或「参考实现」（源码已移除），禁止完整复制生产代码。

## 六、标准结构（复杂组件完整章节顺序）

> 从 `client.md`、`limiter.md`、`retry.md`、`streaming.md`、`streaming_rectifier.md`
> 五份复杂组件文档总结的权威章节顺序。复杂组件文档的编写 / 优化按此结构实施。

```text
# <组件名> 设计文档
> 元信息引用块：模块 / 更新日期 / 职责 / 状态（可选：定位 / 配套 / 工业级对照）

## 📋 目录            全量章节锚点导航（含子小节）

## 设计目标           编号要点：每条一句话，点明「做什么 + 为什么」

## 核心概念解释       每个核心概念一小节：定义 + 关键语义表格/公式 + 直觉解释

## 架构总览           text 代码块画调用链/分层图 + 分层职责表（| 层 | 组件 | 职责 |）

## 组件详解           每个组件一小节：核心接口签名（关键逻辑示意）+ 设计要点/状态表

## 执行流程           步骤流程（text/mermaid 图）；与架构总览互补，不重复描述

## 对外接口           方法表：| 方法 | 同步/异步 | 说明 |（签名含默认值与返回类型）——
                      仅列模块对外暴露的公共接口（被外部文件/调用方依赖的入口），
                      不列 `_` 前缀私有方法与内部辅助函数（实现载体放组件详解）

## 边界情况           编号列表：每个边界 = 触发场景 + 处理行为；关键边界链接 issue

## 配置项清单         配置表（| 配置 | 类型 | 默认 | 说明 |）关联配置项与组件；无配置组件省略

## 测试状态           测试文件（用例数）：覆盖 + 分类要点列表；跨模块间接覆盖一并标注

## 设计决策           仅链接 ADR（决策名 + 一句话结论），不展开描述

## 问题记录           仅链接 issue 文件（问题名 + 编号），不展开描述

## 相关文档           链接主文档 / 同级组件 / 全局框架（可选）
```

### 结构要点

1. **章节固定顺序**：设计目标 → 核心概念解释 → 架构总览 → 组件详解 → 执行流程 → 对外接口 → 边界情况 →
   配置项清单 → 测试状态 → 设计决策 → 问题记录 → 相关文档，自上而下
2. **可省略 / 可扩展**：`配置项清单` 在组件无配置时省略（如 `streaming.md`）；`相关文档` 可选；组件有跨模块配合时
   可在测试状态后、设计决策前插入专属协作节（如 `limiter.md` 的「与重试/熔断的分层配合」）
3. **契约集中、决策外链**：接口契约（对外接口 / 配置项清单）集中成节；**对外接口只收录模块对外暴露的公共接口**
   （被外部文件/调用方依赖的入口，公共方法均可列，含无当前调用者的预留 API），`_` 前缀私有方法、模块级辅助函数
   与内部实现载体**不进此栏**（放组件详解）；对外异常类型（被外部捕获）属跨文件契约，一并列出；设计决策 / 问题记录
   只做 ADR / issue 的导航链接，不展开——双处维护必然漂移（Rule 1「一个事实一个家」）
4. **状态对齐代码**：每节内容与对应 `.py` 当前状态一致，只写当前状态不写历史（Rule 2）；状态徽标 + 更新日期进
   元信息引用块；结构图代码块指定 `text` 语言或 mermaid

## 七、创建 / 优化流程

1. **判定粒度**：按第四节特征判组件类型，选模板。
2. **写前核对代码**：方法签名、配置、边界全部以当前代码为准（不凭记忆）；代码改动后必须同步文档（CLAUDE.md 工作流 gate）。
3. **契约优先**：先写接口契约，再补设计决策。
4. **同步引用**：创建后更新父文档链接（层 README 相关文档列表 + 主文档内指向子文档的「设计文档见 [xxx.md]」）；同时更新 `docs/ALIGNMENT.md` 中该模块的文档列。
5. **校验**：跑 `uv run python -m scripts.verify_alignment`，通过后提交。
6. **避免冗余**：内容与层 README 或主文档重复的部分，只留一处（README/主文档做导航，子文档做详情），不复制。
