## 一、定位与目标

独立子文档是层级 README（总览 + 导航）之下的**单个模块/组件**说明文档，回答两类问题：

- 调用方：「这个组件怎么用？」——接口契约
- 维护者：「为什么这样设计？」——设计动机

**目标**：契约可查、动机可溯、与代码零漂移。子文档不替代代码（Docstring / 测试承载实现与行为），只做契约与决策的权威记录。

## 二、文档类型分类（Diátaxis）

工业界（Diátaxis 框架：Tutorial / How-to / Reference / Explanation）把组件文档拆成两类，**分节隔离，不混写**：

| 类型 | 回答 | 内容 | 面向 |
| --- | --- | --- | --- |
| Reference（使用参考） | 「怎么调用」 | 接口契约：方法签名、参数、返回、配置、异常、行为边界 | 调用方 |
| Explanation（设计解释） | 「为什么这样」 | 设计动机、备选方案、权衡、决策记录 | 维护者 |

同一份子文档可两者兼具，但结构上分离（如「接口契约」节 +「设计决策」节），禁止在叙述中混合。

## 三、工业级原则

1. **docs-as-code**：文档进仓库、随代码同一 review 流程提交；路径镜像源码结构（`app/x/y.py` ↔ `docs/x/y.md`）；用脚本校验对齐（本项目 `scripts/verify_alignment.py` + `docs/ALIGNMENT.md`）。
2. **契约优先**：方法签名、参数默认值、返回结构、配置项等硬契约排最前、最精确。文档中的代码分三类处理：
   - **禁止完整复制生产代码**：实现细节由 docstring 承载，避免双源维护（源码改动需同步文档）
   - **允许关键逻辑示意**：解释设计的核心片段（状态机转移、锁外 sleep、防竞态等）可保留，但须精简并标注「示意，完整实现见源码」
   - **允许参考实现代码**：源码已从生产移除、文档是唯一载体时（如 limiter.md 的 5 类限流算法），完整保留并声明
3. **状态标注**：状态徽标（✅ 已实现 / 🔶 进行中 / ⬜ 待规划 / ❌ 已废弃）+ 更新日期，与 ALIGNMENT 表联动；废弃组件标 ❌ 而非默默消失。
4. **轻量克制**：过度文档化是反模式（documentation rot）。组件越简单，文档越短；文档只做契约与决策的导航，行为的权威在测试。

## 四、粒度分级：简单组件 vs 复杂组件

不是每个组件都要长文档。按复杂度选粒度：

| 判定 | 简单 / 稳定组件 | 复杂 / 高风险组件 |
| --- | --- | --- |
| 特征 | 方法少（≤5）、行为稳定、契约清晰、无重大设计权衡 | 状态多（重试/熔断/限流/整流）、设计有备选方案与权衡 |
| 粒度 | 轻量 Reference（约 80 行） | 完整设计文档（含备选方案对比、决策记录、边界取舍） |
| 结构 | 模板 A（见下） | 模板 B（见下） |
| 本仓库案例 | `cost_tracker.md`（纯静态 4 方法，精简后 82 行） | `limiter.md`（限流，含 5 类算法对比、问题→修复→工业对照） |

**写之前先判定**：组件属于哪类，再选模板。简单组件写成重量文档 = 维护负担；复杂组件写成轻量文档 = 契约不完整。

## 五、标准模板

### 模板 A：简单组件（轻量 Reference，~80 行）

```text
# <组件名> <主题>说明文档
> 元信息引用块：模块 / 更新日期 / 职责 / 状态 / 配套
## 📋 目录
## 定位与职责        ← 2-3 句 + 要点；外部数据（定价表/常量）以源码为准，不整表复制
## 接口契约          ← 方法签名表（类型/默认值/返回结构）+ 公式/关键语义
## 行为边界          ← 容错场景表（None/缺失/非法/边界）
## 使用示例          ← 1-2 段最小示例
## 设计决策          ← 简短：仅关键权衡，如「为什么按长度降序」
## 测试              ← 引用测试文件（行为契约权威来源）
## 相关文档          ← 主文档 + 同级组件 + 配置
```

### 模板 B：复杂组件（完整设计文档）

模板 A 基础上扩展：

```text
## 设计目标 / 核心概念解释
## 架构总览 / 组件详解（每个子组件）
## 调用流程 / 与其它组件的分层配合
## 配置项清单
## 已知边界与设计取舍
## 设计决策记录（问题 → 调研 → 决策 → 实现）
## 工业级对照（备选方案对比表）
## 代码审核与问题修复记录
```

> 组件详解中的代码只允许「关键逻辑示意」（标注出处）或「参考实现」（源码已移除），禁止完整复制生产代码。

## 六、创建 / 优化流程

1. **判定粒度**：按第四节特征判组件类型，选模板。
2. **写前核对代码**：方法签名、配置、边界全部以当前代码为准（不凭记忆）；代码改动后必须同步文档（CLAUDE.md 工作流 gate）。
3. **契约优先**：先写接口契约，再补设计决策。
4. **同步引用**：创建后更新父文档链接（层 README 相关文档列表 + 主文档内指向子文档的「设计文档见 [xxx.md]」）；同时更新 `docs/ALIGNMENT.md` 中该模块的文档列。
5. **校验**：跑 `uv run python -m scripts.verify_alignment`，通过后提交。
6. **避免冗余**：内容与层 README 或主文档重复的部分，只留一处（README/主文档做导航，子文档做详情），不复制。
