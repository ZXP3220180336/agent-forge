# 客户端限流：Token Bucket 算法 + LLM 等待语义

## Context

- 需在到达服务商硬限额前**主动限流**（proactive），避免 429 触发重试风暴；服务商网关限流是第二道闸。
- Agent 场景下工具调用常集中在一小段时间（一次 ReAct 循环连续多次工具调用）——限流器要能处理**瞬时尖峰**。
- LLM 调用与通用 Web API 的失败语义不同：失败成本高（token 白烧、对话中断）、请求**必须要完成才能推进对话**（不是「少一次请求」而是「整条推理链断裂」）。

## Decision

1. **算法选 Token Bucket**：桶容量 = 最大突发量，token 固定速率补充——在「允许突发」和「长期平滑」间取得平衡，适合 Agent 的突发调用模式。对比：漏桶恒定速率严格整形（不支持突发）；固定窗口窗口边界双倍；滑动窗口日志精确但内存随窗口增长。
2. **LLM 限流「等待」（排队）而非「拒绝」**（2026-08-06 决策）：拒绝 = 一次工具调用失败 → Agent 循环中断 → 用户对话卡住。工业 LLM 生态（OpenAI SDK、LiteLLM 等）的客户端限流均为等待型；通用漏桶的「桶满丢弃」是给可丢弃流量（日志/事件）设计的，LLM 调用是**不可丢弃的关键请求**。
3. **对漏桶实现的含义**：`LeakyBucket` 在 LLM 语境下采用**等待型**（桶满排队等空位）而非标准「满则丢弃」——保留恒定输出速率（平滑特性），但请求不失败，符合「透明等待」设计目标。

## Consequences

- **正面**：到达硬限额前主动限流避免 429 重试风暴；允许突发（Agent 工具调用集中）；请求等待配额不失败（对上层无感）；按模型独立记账（main/reasoning/fast 各自配额）。
- **负面**：配额紧张时请求排队累积等待延迟；`LeakyBucket` 等待型偏离标准漏桶语义（文档注明学习参考，未接入生产调用链）。
